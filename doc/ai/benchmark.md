# Benchmarkの設計と更新ガイド

本書は `go-seqpipeline` のベンチマークを実装・更新する開発者およびAIエージェント向けの運用ガイドである。  
利用者向けの性能概要や個別の測定数値はレポートに記載し、本書と混在させない。  
本書の記述と実装に差が生じた場合は、実装・測定条件を確認して整合させる。  

## 目的と公開方針

- **Unit Benchmark** は測定時点の公開APIごとの実行時間・メモリ割り当てなどの性能指標を提供する
- **Scenario Benchmark** は実際の利用に近い組み合わせを同一条件下の実装と比較し、利用者に性能上のトレードオフを示す
- READMEには概要レポートへのリンクと短い説明のみを記載する
- 概要レポートにはScenarioの代表的な測定結果・相対倍率・条件・簡潔な考察を掲載する
- 良い結果だけを選ばない
- 全Unit/Scenarioの集計結果は詳細データとして公開し、測定コードと再現手順も残す
- 公開する結果は**最新の定期更新時点のスナップショット**であり、性能推移、過去との差分、改善・悪化、性能回帰を追跡しない
- 定期更新では現在の結果を再作成・置き換える
- ベンチマークとレポートは**定期更新でまとめて更新する**
- リリース単位では測定しない
- 通常の機能追加・変更PRで公開APIが増減しても即時のベンチマーク追加・レポート更新は必須とせず、次の定期更新でまとめて棚卸し・反映する
- 生データ（`raw.txt` 等）は集計に必要な一時入力であり、Git管理・アーティファクト保管・長期保存のいずれも行わない

## ベンチマークの設計

### Unit Benchmark

- **定期更新時点での** `seq` の公開関数・公開メソッドをソースから洗い出し、対象一覧と測定の対応関係を確認する
- `Seq` / `Seq2` やOperator設定メソッド等も漏らさない
- 定期更新時のコードを基準に公開APIの現行一覧を作成し、その一覧に合わせて測定ケースを追加・修正・削除する
- 通常の機能PRやリリースに測定コードの即時更新を要求しない
- 原則としてAPIごとに独立して測定し、適切な実行条件（入力件数、データ型、分岐条件など）を設ける
- 他実装との比較は意味がある場合に限定する
- 比較がなくても、測定時点の性能指標を再現可能な条件とともに示すことに価値がある
- 単独測定に意味がないAPIは、関連APIの測定に含める
- その場合は対象API・代替ケース・理由を記録する
- 遅延評価のAPIは構築だけを測って性能を代表させない
- 構築と評価が異なる意味を持つ場合は別ケースにする

### Scenario Benchmark

- 基本パイプライン（Map・Filter・収集）、複数段接続、途中終了、Channel変換、Cacheの再利用などを扱う
- 通常ループ・標準iterator・直接Channel操作など、処理結果と測定範囲が比較可能な対照を選ぶ
- 入力件数や段数等の条件を変え、なぜ性能差が出るか読み取れるようにする
- Cacheは初回保存（Fill）、保存済み結果の反復（Warm）、保存費用を含む複数回利用を区別する
- Channelは生成・送受信・goroutine起動・終了待ち・容量などの条件を明記する
- シナリオを追加するときは利用上の意味を説明し、ケース数を増やすこと自体を目的にしない

### 測定の正確性

- 比較対象の出力値、順序、早期停止などが等価であることを通常のテストで検証する
- 入力生成・構築・評価・収集・後片付けのうち、どこまでを計測するか明示し、公平にそろえる
- ループ内で実処理が必ず走るようにし、コンパイラ最適化による不要処理の除去を防ぐ
- `ns/op`、`B/op`、`allocs/op` を基本指標とし、必要に応じて差・倍率・ばらつきを示す
- メモリ保持量と `B/op`（1操作当たりの総割り当て量）は別の指標として扱う
- 小さい性能差、実行環境の違い、GC・温度・OSスケジューリング等の影響を考慮し、測定範囲外の結論は出さない

## データと文書の役割

| 成果物 | 内容 | Git管理 |
| --- | --- | --- |
| ベンチマークコード・等価性テスト | 全APIのUnitと代表Scenario | する |
| 概要レポート | 代表Scenarioの結果と解釈 | する |
| 詳細な集計結果 | 全Unit/Scenarioのケース別測定値 | する |
| 測定方法の詳細 | 環境・条件・計測範囲・再現方法 | する |
| 本ガイド | 設計・更新手順と判断基準 | する |

集計の統計処理には可能な限り `golang.org/x/perf/cmd/benchstat` を利用し、独自集計コードの重複を避ける。  
ベンチマーク名はAPI・シナリオ・条件・実装が識別でき、集計処理でフィルタしやすい形式とする。  
rawは計測中の一時ファイルに限り、処理後に破棄する。  
リポジトリ内の `results/` にrawを配置したり、GitHub Releases・CI Artifacts等へ保存したりしない。  
再集計が必要な場合は保存済みrawを探すのではなく、定期更新手順に従って再測定する。  

## 再測定・レポート更新手順

専用の定期更新 Issue で、次の手順をまとめて実施する。  
パス・コマンド・集計方法を変更した場合は、本ガイドと測定方法も整合させる。  

1. 現行コードの全公開 API と Unit / Scenario を棚卸しし、追加・変更・削除と代替測定の理由を確認する
2. 測定コードをコミットし、Go・OS・CPU・GOMAXPROCS・測定時間・反復回数等の条件を決める
3. 通常テストと等価性テストを実行し、正しさを確認する
4. 同一環境で全件を複数回測定し、raw はリポジトリ外の一時入力に限定する
5. benchstat で集計し、欠測・ばらつき・極端値・警告・比較条件を点検して raw を削除する
6. 詳細集計・概要・測定環境・対象コミットを同じ結果から更新し、数値の手作業転記を避ける
7. 日英 README の導線、コマンド、リンク、raw が残らないことを検証する
8. 今回の対象・条件・検証結果・残事項を Issue / PR に記録する

過去のケースや条件との互換性維持、旧結果との差分分析は不要とする。  
再現性が疑わしい場合は条件を見直して再測定し、失敗した測定から結論を出さない。  

### ファイル配置とコマンド

| パス | 役割 |
| --- | --- |
| `benchmarks/unit_test.go` | Unit と結果検証 |
| `benchmarks/scenario_test.go` | Pipeline / Channel / Cache の Scenario と等価性テスト |
| `benchmarks/API.md` | 今回の公開 API 対応表と代替測定の理由 |
| `benchmarks/METHOD.md` | 測定範囲・ケース名・再現条件・ツール導入 |
| `benchmarks/REPORT.md` | Scenario の代表値・倍率・考察 |
| `benchmarks/results/environment.md` | 今回の環境・対象コミット・測定条件・ツール版 |
| `benchmarks/results/all.{txt,csv}` | 全 Unit / Scenario の集計 |
| `benchmarks/results/{pipeline-loop,pipeline-functions,channel-from,channel-roundtrip,channel-to,cache-reuse}.{txt,csv}` | 同一条件内の比較集計 |
| `benchmarks/measure.sh` | 一時測定・集計・公開表の再作成・raw 削除 |
| `benchmarks/publish.py` | 正常終了・サンプル数の確認と集計済み CSV の整形 |

リポジトリのルートで実行する。  
Go・Python 3・benchstat を用意し、ライブラリ本体の go.mod に測定ツールの依存を追加しない。  

```sh
# ツール導入。実際の版は environment.md に記録される
go install golang.org/x/perf/cmd/benchstat@latest
# 通常テスト・等価性テスト
go test ./... -count=1
# 全件測定・集計・概要更新。raw は処理後に削除される
BENCHSTAT="$(go env GOPATH)/bin/benchstat" sh benchmarks/measure.sh
# 精度と実行コストに応じて条件を選ぶ例
BENCHSTAT="$(go env GOPATH)/bin/benchstat" BENCHTIME=1s COUNT=10 GOMAXPROCS=2 sh benchmarks/measure.sh
```

`GO_BINARY` / `BENCHSTAT` で取得済み実行ファイルを指定できる。  
Go の自動取得を避ける場合は、適切な版の `GO_BINARY` を指定して `GOTOOLCHAIN=local` を付ける。  
`GOCACHE` を省略するとスクリプトが一時ディレクトリ内に作成する。  
再利用できる書き込み先があれば `GOCACHE` を明示してよいが、raw の出力先は変わらない。  
実際に使った `BENCHTIME` / `COUNT` / `GOMAXPROCS` とツールの版は環境記録に出力される。  
測定中は別のテストやビルドを並行実行しない。  

raw はリポジトリ外の `/tmp/seq-benchmark.XXXXXX/raw.txt` だけに出力する。  
成功・失敗・通常の中断で一時ディレクトリ全体を削除する。  
SIGKILL や OS 停止では trap が動かないため、残った該当一時ディレクトリを削除してから再実行する。  
再集計が必要なら過去の raw を探さず、全件を再測定する。  

benchstat の列は `impl` を使い、他の条件が同じ行の実装だけを比較する。  
Warm / Fill は絶対指標にとどめ、構築範囲の異なる Warm / Uncached の倍率は作らない。  
`publish.py` は統計計算をせず、benchstat の中央値と検定結果を整形する。  
定期更新では現在の結果・代表例を見直し、不要になった集計ファイルも削除する。  

### 更新時チェックリスト

- [ ] 全公開関数・メソッドと代替測定の理由を API.md に記録した
- [ ] Unit / Scenario の対象・条件・名前を現行コードに合わせた
- [ ] 比較実装の入力・出力・順序・途中終了などを確認し、等価性テストが通った
- [ ] 測定コードをコミットし、そのコミットで全件を複数回測定した
- [ ] 欠測・信頼区間・検定・警告を確認し、不明確な差を断定していない
- [ ] 詳細集計・概要・測定方法・環境・対象コミットの対応を確認した
- [ ] 現在の結果を置き換え、過去との比較・推移・回帰判定を追加していない
- [ ] README は日英で同期し、文書のコマンド・リンクを検証した
- [ ] raw が追跡されず、今回の一時 raw も残っていない
- [ ] 通常の機能 PR・リリースへの測定義務や、定期実行の自動化を追加していない

## 結果の解釈と比較時の注意

- 絶対時間だけでなく、対照に対する倍率と、計測条件を示す
- Scenarioの比較対象はケースごとに明記する
- 異なる処理や異なる条件の数値を単純比較しない
- 変動の大きい結果は、改善・悪化を断定せず、再測定や条件の確認を優先する
- 比較は同じスナップショット内の公平な対照間に限る
- 過去スナップショットとの数値比較や時系列追跡は行わない
- 概要レポートは網羅性より読みやすさを優先し、詳細データへのリンクで完全性を補う

## 定期更新の運用境界

- 更新の単位は定期更新 Issue とし、リリース単位では実施しない
- 通常の API 追加・変更・削除は、次の定期更新で現行コードを基準にまとめて反映する
- 機能 PR で網羅性が一時的に古くなることを許容する
- 定期更新では棚卸し・ケース見直し・テスト・全件測定・詳細集計・概要を一括で置き換える
- 頻度・実行環境・スナップショットの再作成に必要な手段や自動化は後続 Issue で決める
- 今回はスケジュールや定期実行の自動化を実装しない
- 性能推移・過去との差・改善や悪化・回帰検知の仕組みは作らない
- raw の保管は検討対象にせず、保存するのは測定条件とコミットを記録した集計結果・レポートとする
- 個別の性能問題を調べる追加測定は妨げないが、通常の PR やリリースの全件更新義務にはしない
