# Benchmarkの設計と更新ガイド

本書は `go-seqpipeline` のベンチマークを実装・更新する開発者およびAIエージェント向けの運用ガイドである。  
利用者向けの性能概要や個別の測定数値はレポートに記載し、本書と混在させない。  
本書の記述と実装に差が生じた場合は、実装・測定条件を確認して整合させる。  

## 目的と公開方針

- **Unit Benchmark** は各 API と、それを使わない一般的な同一処理を比較し、API を選ぶ際の時間・割り当ての費用を示す
- **Scenario Benchmark** は実際の利用に近い組み合わせを同一条件下の実装と比較し、利用者に性能上のトレードオフを示す
- README には性能概要へのリンクだけを載せる
- 概要レポートにはScenarioの代表的な測定結果・相対倍率・条件・簡潔な考察を掲載する
- 良い結果だけを選ばない
- 全Unit/Scenarioの集計結果は詳細データとして公開し、測定コードと再現手順も残す
- 公開する結果は**最新の定期更新時点のスナップショット**であり、性能推移、過去との差分、改善・悪化、性能回帰を追跡しない
- 定期更新では現在の結果を再作成・置き換える
- ベンチマークとレポートは**定期更新でまとめて更新する**
- リリース単位では測定しない
- 通常の機能追加・変更PRで公開APIが増減しても即時のベンチマーク追加・レポート更新は必須とせず、次の定期更新でまとめて棚卸し・反映する
- 生データ（`raw.txt` 等）は集計に必要な一時入力であり、Git管理・アーティファクト保管・長期保存のいずれも行わない

## 読者と情報の置き場所

| 文書 | 読者にしてほしいこと | 残す情報 |
| --- | --- | --- |
| README | 性能概要を開く | リンクのみ |
| `benchmarks/REPORT.md` | 一瞥で利用上のトレードオフをつかむ | 少数の代表値・倍率・割り当て量・短い解釈 |
| `results/unit.md` | 使う API の費用を探す | 全 API の値・測定範囲・統計の凡例 |
| `results/scenario.md` | 自分の利用条件に近い実装を比較する | 同条件の対照・時間・割り当て・検定 |
| `benchmarks/METHOD.md` | 自分の用途に当てはまる測定か判断する | 入力・出力・処理内容・計測範囲・比較上の注意 |
| `results/environment.md` | どの版・環境の結果か確認する | 日時・対象コード・Go・OS・CPU・実行条件 |
| 本ガイド・`benchmark-api.md` | 次の測定と公開を実施する | 棚卸し・配置・コマンド・検証・保存・更新方針 |

各文は、ないと利用者が何を誤解するかを説明できるものだけ残す。  
「担当者が何をしたか」「次に何をすべきか」は利用者向けに書かず、ここへ置く。  
利用者が結果を選ぶのに必要な条件と、担当者が測定を再現する手順を混同しない。  
`METHOD.md` もライブラリ利用者が測定結果の適用範囲を判断するための文書であり、ベンチマークの実装方針や AI への指示は書かない。  
入力・処理・出力・計測範囲は結果の解釈に必要な条件として記載し、入力元をそろえる理由や測定対象以外の処理を分離する方針は本書に置く。  
たとえば「Seq.Pipe2 で値と変換値の組を作る」は測定内容だが、「Zip を他の測定に混ぜない」は実装方針である。  
公開文書を更新する際は、Issue の対応内容や本書の設計規則を、そのまま測定条件として転記しない。  
概要に P 値や全条件を詰め込まず、詳細表へ導く。  
表の共通条件は見出し・本文に置き、セルには短いラベルや一つの測定値を置く。  
概要は実装を別行に、詳細の時間比較は実装を別列にし、矢印やセル内改行で値を連結しない。  
詳細の検定は同条件の比較ごとに折りたたみ、指標・増減率・検定結果を列に分ける。  
公開文書の説明は必要な場所に一度だけ置き、細かい統計は条件・凡例の参照で補う。  

参照：[benchstat の比較列](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat#hdr-Configuring_comparisons)、[ケース間比較の解説](https://www.bwplotka.dev/2024/go-microbenchmarks-benchstat/)。  

## 集計の実装

`measure.sh` は通常テスト、全件測定、benchstat の全件・比較 CSV、一時 Markdown 生成、公開ファイル置き換えを順に行う。  
`publish.py` は全ケースの 3 指標と比較検定がそろい、全件 CSV と比較 CSV の中央値・信頼区間が一致することを確認する。  
全指標が詳細表で使われていない場合は公開を失敗させる。  
概要の代表ケースはコードで選び、値は同じ集計結果から取得する。  
`publish.py` は測定コミットの Go ソースから関数宣言行を読み、実装名・時間列を対応する処理関数へリンクする。  
同じ処理の `Benchmark...` / `Test...` が存在しない場合や、全処理にリンクできない場合は公開を失敗させる。  
リンクは測定コミットに固定し、通常の機能変更でファイルの行が移動しても参照先がずれないようにする。  
公開文書を直すときは生成元も修正し、次の測定で古い説明が復活しないことを確認する。  
ツールの版を変更する場合はこの導入コマンドも更新し、公開先にコマンドや作業履歴を埋め込まない。  

## ベンチマークの設計

### Unit Benchmark

- **定期更新時点での** `seq` と `op` の公開関数・公開メソッドをソースから洗い出し、対象一覧と測定の対応関係を確認する
- `Seq` / `Seq2` やOperator設定メソッド等も漏らさない
- 定期更新時のコードを基準に公開APIの現行一覧を作成し、その一覧に合わせて測定ケースを追加・修正・削除する
- 通常の機能PRやリリースに測定コードの即時更新を要求しない
- 原則としてAPIごとに独立して測定し、適切な実行条件（入力件数、データ型、分岐条件など）を設ける
- 標準の処理を置き換える各 API に Go の比較実装を用意し、入力・処理・出力・収集・結果保持・終了待ちをそろえる
- Compose / Compose2 は 4 種類の入出力で同じ 4 段のオペレーターを直接接続した実装と比較し、両側とも構築・接続・全件反復を計測に含める
- 直接接続側を事前合成せず、`noinline` や比較用の実行時ディスパッチで通常の最適化を抑えない
- Cache / Cache2 は標準 API の代替ではないため Unit を設けず、保存と再利用を Scenario で測る
- Unit は Library の入力元と同じ標準 iterator を用い、スライス直接反復と iterator 反復の差を混ぜない
- `FromSlice` は `slices.Values`、Seq2 のスライス入力は `slices.All`、`FromMap` は `maps.All` に対応させる
- Seq2 の生成・反復・変換・パイプ接続に Zip を混ぜず、Zip 自体のケースで独立して測定する
- Seq.Pipe2 は単一入力から組を返す変換を使い、Go 側も同じ入力・変換・出力・評価・結果保持にそろえる
- Seq.Pipe2 は両実装とも `slices.Values`、Seq2.Pipe は両実装とも `slices.All` を入力元とする
- Keys / Values は map を受け取り、`FromMap(...).Pipe(...)` と `maps.All` からの射影を比較する
- 通常の最適化は有効とし、結果を演算子単独の費用とは解釈しない
- 比較する両実装の計測範囲・結果保持をそろえ、代表入力で処理を実行できることを確認する
- 単独測定に意味がないAPIは、関連APIの測定に含める
- その場合は対象API・代替ケース・理由を記録する
- 遅延評価のAPIは構築だけを測って性能を代表させない
- 構築と評価が異なる意味を持つ場合は別ケースにする

### Scenario Benchmark

- 基本パイプライン（Map・Filter・収集）、複数段接続、途中終了、Channel変換、Cacheの再利用などを扱う
- 通常ループ・標準iterator・直接Channel操作など、処理結果と測定範囲が比較可能な対照を選ぶ
- 入力件数や段数等の条件を変え、なぜ性能差が出るか読み取れるようにする
- Cacheは初回保存（Fill）、保存済み結果の反復（Warm）、保存費用を含む複数回利用を区別する
- Fill の疎通テストでは、代表入力の保存結果も確認する
- Channelは生成・送受信・goroutine起動・終了待ち・容量などの条件を明記する
- Channel の表は Seq 入力と Channel 入力に分け、入力 channel のない Seq / ToChannel に入力容量を表示しない
- シナリオを追加するときは利用上の意味を説明し、ケース数を増やすこと自体を目的にしない

### コードの配置

- Unit / Scenario を分離した上で、Map / Filter / Take / Skip などの機能ごとにファイルを分ける
- 対応する Seq / Seq2 は同じファイルへ置いてよいが、各機能を対象の処理・比較対象の処理・ベンチマーク・テストの順に連続して記述する
- Unit は機能別の `*_test.go`、Scenario は機能別の `*_scenario_test.go` へ分け、同じファイルにケースを混在させない
- 複数機能を組み合わせる Scenario は独立した機能群として扱う
- 各 API・実装に `mapLibrary` / `mapGo` のような処理全体の関数を用意する
- Library は `source := seq.FromSlice(...).Pipe(...)` などで接続を終えてから `for ... range source` で評価する
- 比較する実装は `BenchmarkMap` / `TestMap` のように、1 機能につき 1 つのベンチマーク関数・テスト関数へまとめる
- 比較対象のない機能も、処理・ベンチマーク・テストの順に記述する
- ベンチマークでは処理関数を格納するケース登録表・汎用状態構造体・共通の測定ループを作らず、処理全体と低水準の入力生成などに共通化を限る
- 各 `b.Run` / `t.Run` に実装だけを囲む中間の `Run` を設けない
- 入力件数・段数・モードなどの繰り返す測定条件は、各ベンチマークに必要な小さなパラメータテーブルにまとめる
- 比較対象ごとに同じテーブルを走査して `b.Run` を実行し、比較対象がない場合も繰り返す条件をテーブルにまとめる
- テーブルは計測ループの外に置き、完全なケース名・順序・件数・条件、入力準備と処理の測定範囲を保つ
- ベンチマーク名には実装と入力条件を含む既存の項目を保ち、テスト名にも実装と固有の条件を含める
- ベンチマークは各条件で入力を用意し、`for b.Loop()` 内から処理関数を直接呼ぶ
- 各処理のテストは正常系の代表入力による疎通確認に絞り、比較対象の名前と処理関数をテーブルにまとめ、`t.Run` 内の呼び出しと期待値の比較を共有する
- テストの入力・処理条件・期待値は固定し、シグネチャや固定引数が異なる処理は短い関数でそろえ、数値パラメータの組み合わせをテーブルへ展開しない
- テストの整理でも既存の入力・期待値・ケース名・件数・実行順を保ち、可変状態の独立性と共有結果変数による直列実行の制約を維持する
- 境界値・入力サイズ・全測定条件の検証をテストへ展開せず、ライブラリ本体の仕様検証は `seq` と `op` のテストに任せる
- Seq の生成・演算子の構築・評価・収集は処理本体に含める
- Cache の Fill / Warm / Reuse は別関数にし、Warm だけは保存済み入力を処理関数へ渡す
- 入力データと Warm の保存処理は `b.Loop()` より前に置く
- `b.Loop()` の初回呼び出しで時間・割り当ての計測がリセットされるため、その準備を除くための `ResetTimer()` は不要
- 測定分類は `class`、比較軸は `api`・`phase`・`kind`・`N`・`impl` 等の名前で識別する
- 定期更新で追加する機能も同じ構成にし、全件の試行実行で条件の欠落・重複を確認する

配置や入口名だけを整理する場合は、処理本体・直接呼び出し・計測範囲・入力条件・期待値を保つ。  
再計測を伴わない整理では、公開済みの測定値・日時・対象コミットと、そのコミットに固定したソースリンクを維持する。  

ファイルの分割だけを目的に細分化せず、機能のまとまりと保守性を優先する。  
処理と入口の対応・ファイル一覧は [API 対応表](benchmark-api.md) に記録する。  
測定する範囲を変えた場合は、全件を測り直して結果・測定条件をそろえる。  
Issue #86 は以下の Compose 部分更新を例外とする。  

### 測定の正確性

- 代表入力のテストで比較対象の出力が一致することを確認し、全ベンチマークの試行実行で疎通を確認する
- 入力生成・構築・評価・収集・後片付けのうち、どこまでを計測するか明示し、公平にそろえる
- ループ内で実処理が必ず走るようにし、コンパイラ最適化による不要処理の除去を防ぐ
- `ns/op`、`B/op`、`allocs/op` を基本指標とし、必要に応じて差・倍率・ばらつきを示す
- メモリ保持量と `B/op`（1操作当たりの総割り当て量）は別の指標として扱う
- 小さい性能差、実行環境の違い、GC・温度・OSスケジューリング等の影響を考慮し、測定範囲外の結論は出さない

## データと文書の役割

| 成果物 | 内容 | Git管理 |
| --- | --- | --- |
| ベンチマークコード・疎通テスト | API 別の Unit と利用目的別の Scenario | する |
| 概要レポート | 代表Scenarioの結果と解釈 | する |
| 詳細な集計結果 | 全Unit/Scenarioのケース別測定値 | する |
| 測定方法の詳細 | 環境・条件・計測範囲・再現方法 | する |
| 本ガイド | 設計・更新手順と判断基準 | する |

集計の統計処理には可能な限り `golang.org/x/perf/cmd/benchstat` を利用し、独自集計コードの重複を避ける。  
ベンチマーク名はAPI・シナリオ・条件・実装が識別でき、集計処理でフィルタしやすい形式とする。  
raw と benchstat の TXT・CSV は一時入力・中間データに限り、処理後に破棄する。  
リポジトリ内の `results/` には公開用 Markdown だけを置き、raw・TXT・CSV を GitHub Releases・CI Artifacts 等にも保存しない。  
再集計が必要な場合は保存済みrawを探すのではなく、定期更新手順に従って再測定する。  

## 再測定・レポート更新手順

専用の定期更新 Issue で、次の手順をまとめて実施する。  
パス・コマンド・集計方法を変更した場合は、本ガイドと測定方法も整合させる。  

1. 現行コードの全公開 API と Unit / Scenario を棚卸しし、追加・変更・削除と代替測定の理由を確認する
2. 測定コードをコミットし、Go・OS・CPU・GOMAXPROCS・測定時間・反復回数等の条件を決める
3. 通常テストと等価性テストを実行し、正しさを確認する
4. 同一環境で全件を複数回測定し、raw はリポジトリ外の一時入力に限定する
5. benchstat で集計し、欠測・ばらつき・極端値・警告・比較条件を点検して raw を削除する
6. 詳細集計・概要・測定環境・対象コミットを同じ結果から更新し、数値の手作業転記を避ける
7. 日英 README の導線、コマンド、リンク、raw が残らないことを検証する
8. 今回の対象・条件・検証結果・残事項を Issue / PR に記録する

過去のケースや条件との互換性維持、旧結果との差分分析は不要とする。  
再現性が疑わしい場合は条件を見直して再測定し、失敗した測定から結論を出さない。

リポジトリのルートで実行する。  
Go・Python 3・benchstat を用意し、ライブラリ本体の go.mod に測定ツールの依存を追加しない。  
Go の版は `go.mod` に合わせ、集計ツールの版は実行時に確認する。  

```sh
# 測定に使う集計ツールを明示して導入
go install golang.org/x/perf/cmd/benchstat@v0.0.0-20261009192801-be2c69fb417e
# 通常テスト・等価性テスト
go test ./... -count=1
python3 -m unittest discover -s benchmarks -p 'test_*.py'
# 全件測定・集計・概要更新。raw は処理後に削除される
BENCHSTAT="$(go env GOPATH)/bin/benchstat" sh benchmarks/measure.sh
# 測定条件を明示する例
BENCHSTAT="$(go env GOPATH)/bin/benchstat" BENCHTIME=500ms COUNT=10 GOMAXPROCS=2 sh benchmarks/measure.sh
```

`GO_BINARY` / `BENCHSTAT` で取得済み実行ファイルを指定できる。  
Go の自動取得を避ける場合は、適切な版の `GO_BINARY` を指定して `GOTOOLCHAIN=local` を付ける。  
`GOCACHE` を省略するとスクリプトが一時ディレクトリ内に作成する。  
再利用できる書き込み先があれば `GOCACHE` を明示してよいが、raw の出力先は変わらない。  
実際に使った `BENCHTIME` / `COUNT` / `GOMAXPROCS` は環境記録に出力される。  
既定値は各ケース `500ms × 10`（計測時間の目標は合計 5 秒）、`GOMAXPROCS=2` とする。  
2026-10-26 の公開結果は `5s × 10` で取得済みのため再測定せず保持し、次回の定期更新から新しい既定値を使う。  
`COUNT` 巡、全ケースを各 1 回測り、比較する両実装が巡ごとに繰り返されるようにする。  
片方を全回数測ってから他方を測る順序を避け、各ケースの測定時間と総サンプル数は変えない。  
測定中は別のテストやビルドを並行実行しない。  

raw・benchstat CSV・環境記録用の中間ファイルはリポジトリ外の `/tmp/seq-benchmark.XXXXXX/` にだけ出力する。  
成功・失敗・通常の中断で一時ディレクトリ全体を削除する。  
SIGKILL や OS 停止では trap が動かないため、残った該当一時ディレクトリを削除してから再実行する。  
再集計が必要なら過去の raw を探さず、全件を再測定する。  

benchstat の列は `impl` を使い、他の条件が同じ行の実装だけを比較する。  
Unit の名前には `class=Unit`・`api`・`N`・`phase`・`ref`・`impl` を含め、`ref` は対照の処理、`impl` は比較する実装を表す。  
Compose / Compose2 は Pipe / Composed、その他は Go / Library を使う。  
`benchstat -ignore .name -filter "/class:Unit /impl:(Go OR Library)" -col "/impl@(Go Library)" -format=csv` で同じスナップショット内を比較し、条件を行から除外しない。  
Compose / Compose2 は `/impl:(Pipe OR Composed)` と `/impl@(Pipe Composed)` で別の比較 CSV にする。  
`.name` は機能ごとの入口名なので比較の行から除き、`class` と処理条件は残す。  
Cache の Warm / Fill は単独の Scenario として掲載し、構築範囲の異なる Warm / Uncached の倍率は作らない。  
Scenario の比較相手がない Warm / Fill は全件掲載する。  
`publish.py` は統計計算をせず、benchstat の中央値・信頼区間・検定結果を Markdown に整形する。  
全 API・全 Scenario と全指標を詳細表に掲載し、API 名や条件を長いケース名から分離する。  
各ケースの ns/op・B/op・allocs/op の存在と公開表への掲載、比較 CSV と全件 CSV の一致を検証する。  
未知の API・Scenario も詳細表に自動追加し、Unit は全ケースの期待する実装対がそろわなければ失敗させる。  
Scenario の比較対象がないケースも省略しない。  
概要の代表例だけは定期更新時に選択を見直し、値を手動転記しない。  
生成・検証がすべて成功してから現在の公開 Markdown を置き換える。  
定期更新では現在の結果・代表例を見直し、不要になった集計ファイルも削除する。

## 結果の解釈と比較時の注意

- 絶対時間だけでなく、対照に対する倍率と、計測条件を示す
- Unit / Scenario の比較対象はケースごとに明記する
- 異なる処理や異なる条件の数値を単純比較しない
- 変動の大きい結果は、改善・悪化を断定せず、再測定や条件の確認を優先する
- 比較は同じスナップショット内の公平な対照間に限る
- 過去スナップショットとの数値比較や時系列追跡は行わない
- 概要レポートは網羅性より読みやすさを優先し、詳細データへのリンクで完全性を補う

## 定期更新の運用境界

- 更新の単位は定期更新 Issue とし、リリース単位では実施しない
- 通常の API 追加・変更・削除は、次の定期更新で現行コードを基準にまとめて反映する
- 機能 PR で網羅性が一時的に古くなることを許容する
- 定期更新では棚卸し・ケース見直し・テスト・全件測定・詳細集計・概要を一括で置き換える
- 更新要否の確認と専用 Issue の作成は、毎週月曜 09:17 JST の GitHub Actions で行う
- 測定環境・条件の選択、ベンチマークの見直し・再測定・レポート更新は、作成された Issue で実施する
- 性能推移・過去との差・改善や悪化・回帰検知の仕組みは作らない
- raw の保管は検討対象にせず、保存するのは測定条件とコミットを記録した集計結果・レポートとする
- 個別の性能問題を調べる追加測定は妨げないが、通常の PR やリリースの全件更新義務にはしない

### 週次チェックと比較基準

`.github/workflows/benchmark-update.yml` は `Asia/Tokyo` のスケジュールと手動実行に対応する。  
main でのみ実行し、チェック開始時点の `origin/main` を固定して比較する。  
定期実行と手動実行は同じ concurrency グループで直列化し、実行中のチェックをキャンセルしない。  
権限は `contents: read` と `issues: write` に限定する。  
GitHub のスケジュール実行には遅延があり、公開リポジトリでは 60 日間操作がないと無効化されるため、実行履歴も確認する。  
仕様は [GitHub Actions の schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) を参照する。  

比較基準は、main 上の `benchmarks/results/environment.md` の「対象コード（ライブラリ・測定）」行にある完全なコミット SHA とする。  
行は一意で、リンク先リポジトリと省略 SHA が完全な SHA と一致することを検証する。  
別の基準ファイル、変数、Issue のクローズ日時は使わない。  
squash merge 後の測定コミットがローカルにない場合は、origin からその SHA を取得する。  
祖先関係に依存する差分ではなく、測定コミットと確認対象コミットのファイル内容を直接比較する。  
変更を取り消して元の実装に戻っていれば、対象差分なしになる。  

判定はファイル単位で行い、対象を次に限定する。  

- ライブラリ・依存コードの `.go` ファイル（`*_test.go` と `doc.go` を除く）
- ルートの `go.mod`、`go.sum`、`go.work`、`go.work.sum`、`.go-version`、`.tool-versions`

`benchmarks/`、`ci/`、`doc/`、`.github/` と、各階層の `testdata/` は対象外とする。  
文書・テスト・測定コード・測定結果のみの変更では Issue を作らない。  
実装ファイル内のコメントのみの変更は、同じファイルの変更として対象になる。  
追加・削除も確認し、実装ファイルがテストへ移動した場合は元の実装の削除として検出する。  

未完了 Issue の本文に、独立した行として `<!-- go-seqpipeline:benchmark-update -->` がある場合は新規作成を見送る。  
Issue 一覧は全ページ取得し、PR と通常の計画 Issue は判定から除く。  
タイトルやラベルの変更では識別が失われないが、識別行は完了まで削除しない。  
更新を取りやめて Issue を閉じても比較基準は変わらないため、対象差分が残れば次のチェックで再作成する。  

| 状況 | 判定 |
| --- | --- |
| 対象差分なし | 正常終了し、Issue を作成しない |
| 未完了の更新 Issue あり | 正常終了し、既存 Issue のリンクを記録する |
| 対象差分あり | 比較リンク・対象ファイル・更新チェックリストを含む Issue を作成する |
| 測定結果・レポートがまだない | 重複を確認して初回測定 Issue を作成する |
| 結果はあるが実行環境レポートがない、または SHA が不正 | 失敗する |
| Git・API の失敗、測定コミットを取得できない | 失敗する |

結果と比較コミットはログと Actions の実行サマリーに記録する。  
Issue を作成しただけでは基準を更新しない。  
更新 Issue の作業で測定コードをコミットしてから `benchmarks/measure.sh` を実行し、実際の測定対象コミットと測定日時をレポートへ記録する。  
生成したレポートを main に反映してから Issue を完了し、そのレポートの測定コミットを次の比較基準とする。  
Issue 作成時の確認コミット以降にも変更がある場合は、更新時点のコードを測定してよい。  

### 手動確認と検証

Actions の **Benchmark update** を main に対して手動実行する。  
`dry-run` は既定で有効であり、Issue 作成が必要なら予定本文をサマリーへ出力する。  
実際に Issue を作成する場合は `dry-run` を無効にする。  
dry-run でも基準の検証と既存 Issue の照合は行い、エラーを対象差分なしとして扱わない。  

ローカルではリポジトリのルートで実行し、Python 3・Git・認証済みの GitHub CLI を用意する。  
追加の Python パッケージは不要である。  

```sh
git fetch origin main
python3 ci/scripts/check_benchmark_update.py --repo meian/go-seqpipeline --dry-run
python3 -m unittest discover -s ci/scripts -p 'test*benchmark*.py'
```

判定関数の単体テストと、一時 Git リポジトリによる統合テストを分ける。  
統合テストでは Issue API を代替し、実際の Issue を作成せず、実装・設定の変更、除外対象、削除・移動、取り消し、履歴が分岐した測定コミット、初回、重複、基準更新、dry-run、異常系を確認する。  
CI の README policy ジョブで、リポジトリ用スクリプトのテストとして README ガードとともに実行する。
