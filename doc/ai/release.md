# リリースの版番号決定

この文書は、前回の正式版からの変更に応じて、次の版番号とリリースノートに載せる内容を決める基準を定める。  
タグや GitHub Release の作成手順は扱わない。  

## 表記とタグ

正式版のタグは `vMAJOR.MINOR.PATCH` とする。  
各番号は先頭にゼロを付けない非負整数とし、既存の `v0.1.0` もこの形式に従う。  
プレリリース版には、予定する正式版の番号に `-alpha.N`、`-beta.N`、`-rc.N` のいずれかを付け、`N` は 1 から増やす。  
例えば `v0.2.0-rc.1` の後に出す正式版は `v0.2.0` とする。  
正式版の公開後に、同じ番号のプレリリース版は作らない。  
タグにはビルドメタデータ（`+...`）を付けない。  

## 版番号の選び方

前回の正式版から次の正式版までに含める変更をまとめて判定する。  
互換性を壊す変更、互換性を保つ機能追加、不具合修正の順に優先し、最も上位の変更に合わせて版番号を一度だけ進める。  

| 変更内容 | `v0.x` の次版 | `v1` 以降の次版 |
| --- | --- | --- |
| 互換性を壊す変更 | minor を増やし、patch を 0 に戻す | major を増やし、minor と patch を 0 に戻す |
| 互換性を保つ機能追加 | minor を増やし、patch を 0 に戻す | minor を増やし、patch を 0 に戻す |
| 互換性を保つ不具合修正・内部変更 | patch を増やす | patch を増やす |

`v0.x` は安定性や後方互換性を保証しないが、このリポジトリでは互換性を壊す変更を patch に含めない。  
`v1.0.0` は公開 API を安定版として定めるときに選び、`v0.x` の互換性を壊す変更から自動的に移行しない。  
`v2` 以降の major 更新では、Go モジュールのパスに `/v2` などの suffix が必要になる。  

## 互換性の判断

公開 API の追加・削除・変更によって既存の利用コードに修正が必要になる場合は、互換性を壊す変更とする。  
型が変わらなくても、GoDoc や利用ガイドで示した結果、評価・停止・nil などの動作契約を変える場合は同様に扱う。  
契約に反する不具合を契約どおりに直す場合は、互換性を保つ修正として扱う。  

`go.mod` の `go` 行で定める最低 Go バージョンを引き上げる場合は、以前の Go で利用できなくなるため互換性を壊す変更とする。  
最低 Go バージョンを下げて対応範囲を広げる場合は、互換性を保つ機能追加とする。  
CI で使う Go のバージョンだけを変えても、最低 Go バージョンの変更には含めない。  

例えば `v0.1.0` から、公開 API の追加や最低 Go バージョンの引き上げを含む次の正式版は `v0.2.0` とする。  
互換性を保つ不具合修正だけなら `v0.1.1` とする。  
機能追加と不具合修正が同時に入る場合は minor を選ぶ。  

## 文書とベンチマーク

文書は原則としてリリース版ごとに分けず、現在の仕様に合わせて更新する。  
文書だけの変更は版番号の判定材料にしない。  
文言修正や細かな項目追加はリリースノートに載せない。  
章立ての整理や大幅な書き換えは、リリースノートに載せるかをその都度ユーザーに確認する。  
機能や動作の変更に伴う文書修正は、元の機能や動作の変更で版番号を判定する。  

ベンチマークの測定結果・レポート・測定コードの更新だけでは版番号を進めず、リリースノートにも載せない。  
性能改善を含む実装の変更は、実装の公開契約への影響で版番号を判定する。  

版番号の形式と Go モジュールの扱いは [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) と [Go Modules Reference](https://go.dev/ref/mod) を基にする。
