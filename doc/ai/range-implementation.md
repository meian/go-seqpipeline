# Issue #30: 数値 Seq の実装判断ルール

この文書は [仕様境界](range-contract.md) と [ドラフト PR #74](https://github.com/meian/go-seqpipeline/pull/74) のコメントに基づく内部実装の判断を記録する。  
`reflect.TypeFor[T]().Kind()` で型を振り分け、signed / unsigned をそれぞれ 1 関数で実装する。  
比較に使った試作コードを新しいブランチへ移植する前提にはしない。  

## 採用する構成

- 公開入口は generic な `seq.FromRange` とし、型の振り分けはシーケンス構築時に 1 回行う
- `reflect.Kind` に応じて signed / unsigned の実装を選び、反復する要素ごとに反射を使わない
- `reflect.Uintptr` を unsigned の経路に含め、定義型も元の型 `T` の値として返す
- signed / unsigned の内部関数は別にし、幅や符号を失う変換を避ける

## 実装時に守る条件

- 公開契約を先に確定し、`seq` に入力生成関数を置く
- 反復中の現在値と終了判定を呼び出しごとのローカル状態に置き、途中停止後の再評価に影響を残さない
- `yield` が `false` を返したら次の値を計算せずに戻る
- 仕様で対象にする方向と型を区別し、型変換で値を失わない
- 次の値を計算する前に端点と型の範囲を確認し、折り返しや停止しない反復を防ぐ
- `-math.MinInt` や符号付き整数の最大・最小をまたぐ減算を安全だと仮定しない
- 空結果のために nil の `Seq` を返さない

## 比較結果と採用理由

11 型別関数と signed / unsigned の 2 関数を、組み込み型の `type switch` と定義型への `reflect` fallback、および `reflect` のみの分岐で比較した。  
型別関数と 2 関数はいずれも generic であり、非 generic の具象関数を比較した結果ではない。  
比較は [PR #68](https://github.com/meian/go-seqpipeline/pull/68) 由来の試作を独立したモジュールに置き、Apple M4・Go 1.27.3・darwin/arm64・`GOMAXPROCS=1` で行った。  
Range の生成と全要素の消費を合わせ、昇順・降順とも `step` の大きさを 1 とした。  

次は `reflect` のみで振り分けた型別関数と 2 関数の中央値を比較した結果である。  

| 条件 | 型 | 時間差 |
| --- | --- | --- |
| 96 要素の昇順 | `int8` | 29.5% 短い |
| 96 要素の昇順 | `uint16` | 21.2% 短い |
| 96 要素の昇順 | `uint32` | 27.7% 短い |
| 4096 要素の昇順 | `uint16` | 26.5% 短い |
| 4096 要素の昇順 | `uint32` | 36.2% 短い |
| 4096 要素の降順 | `uint` | 6.1% 短い |
| 4096 要素の降順 | `uintptr` | 12.1% 短い |

`type switch` と `reflect` の差は全 81 条件の中央値で絶対値 0.5% 未満だった。  
割り当ては全方式で Range の呼び出し 1 回につき 3 回だった。  

2 関数は一部の型と長い反復で有利で、11 型別関数より実装箇所も少ない。  
`reflect` のみの振り分けには今回の測定で明確な劣位がなく、組み込み型と定義型で別の分岐方式を保つ必要がない。  
このため、2 関数と `reflect` の組み合わせを採用する。  
`int32` の優劣は追加測定でも定まらず、呼び出し回数が多い条件では方式間の差が小さい。  
測定は生成単体と生成済み `Seq` の再利用を分けておらず、1 以外の `step` も含まないため、すべての利用条件で速いという結論にはしない。  

## 実装後の確認と再測定条件

まず採用方式が確定した公開契約を満たすことをテストで確認する。  
新しいコードが試作と異なる処理経路になる場合は、短い列と長い列、生成ごとの評価と生成済み `Seq` の再利用を分けて測る。  
Go・CPU の更新や主な利用形態の変化で判断が変わり得る場合も、同じ条件で再測定する。  
性能を再確認するときは `ns/op`・`allocs/op` を記録し、測定順を逆にした実行でも差が再現するか確認する。  

## 検証と文書

公開契約が確定したら、`seq` の単体テストでは端点への到達・飛越し、終点から遠ざかる `step`、0、狭い整数型を超える `step`、最大・最小値、定義型、再評価を確認する。  
`Pipe`・収集・途中停止の連携は単体テストと分けて検証する。  
公開後の個別仕様は GoDoc、実行可能な使い方は `seq` の Example に置く。  
README は入口に保ち、利用ガイドへ追記する場合は日英を同じ変更で更新する。
