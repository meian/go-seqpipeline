# Issue #30: 数値 Seq の実装判断ルール

この文書は [仕様境界の提案](range-contract.md) を確定した後、内部実装を選ぶための基準である。  
実装方式はまだ採用していない。  
過去の試作や測定結果は候補を絞る参考に限り、新しいブランチへコードを移植する前提にしない。  

## 実装時に守る条件

- 公開契約を先に確定し、`seq` に入力生成関数を置く
- 反復中の現在値と終了判定を呼び出しごとのローカル状態に置き、途中停止後の再評価に影響を残さない
- `yield` が `false` を返したら次の値を計算せずに戻る
- 仕様で対象にする方向と型を区別し、型変換で値を失わない
- 次の値を計算する前に端点と型の範囲を確認し、折り返しや停止しない反復を防ぐ
- `step` を `int` とする場合、`-math.MinInt` や符号付き整数の最大・最小をまたぐ減算を安全だと仮定しない
- 空結果のために nil の `Seq` を返さない

## 比較する実装の軸

以下は整数型とその定義型を対象にする場合の比較候補である。  

| ループの分け方 | 型の振り分け方 | 確認する費用 |
| --- | --- | --- |
| 組み込み整数の型別関数 | 組み込み型を `type switch`、定義型を別経路 | 関数数と反復速度 |
| 組み込み整数の型別関数 | `reflect.TypeFor[T]().Kind()` | 振り分け費用と反復速度 |
| signed / unsigned の 2 系統 | 組み込み型を `type switch`、定義型を別経路 | 共通化による分岐と反復速度 |
| signed / unsigned の 2 系統 | `reflect.TypeFor[T]().Kind()` | 共通化と振り分けの総費用 |

上の 4 方式は比較対象であり、すべてを製品コードに追加する指示ではない。  
`type switch` は型の完全一致であり、`type MyInt int` は `case int` に一致しない。  
基底型が同じ定義型を受ける経路を別に設け、組み込み型だけ速くても定義型の契約を失わない。  
型別の具体関数を比較する場合は、その関数が実際に非 generic であることをシグネチャで確認する。  

## 採用の判断

1. 全候補に同じ仕様テストを通し、正しさを先にそろえる
2. 短い列の反復、長い列の反復、毎回の生成、生成済み `Seq` の再利用を分けて測る
3. signed / unsigned、幅の異なる型、定義型、昇順・降順、途中停止を代表条件に含める
4. `ns/op` と `allocs/op` を確認し、測定順を逆にして再実行する
5. 再現した実利用上の差が保守負担を上回る方式だけを採用する

過去の試作では 2 系統の関数が一部の型で速く、`type switch` と `reflect` の差は一貫して大きくなかった。  
その結果は旧コードと当時の Go・CPU に依存し、新しい実装の採用理由としては再測定が必要である。  
測定条件と採用案が決まったら、比較した方式、再現した差と結論の出ない差、採用理由、受け入れる欠点をこの文書に追記する。  
Go の更新や主な利用形態の変化で結論が変わり得る場合は、その再測定条件も残す。  

## 検証と文書

仕様境界の提案を採用する場合、`seq` の単体テストでは端点への到達・飛越し、方向不一致、0、狭い整数型を超える `step`、最大・最小値、定義型、再評価を確認する。  
`Pipe`・収集・途中停止の連携は単体テストと分けて検証する。  
公開後の個別仕様は GoDoc、実行可能な使い方は `seq` の Example に置く。  
README は入口に保ち、利用ガイドへ追記する場合は日英を同じ変更で更新する。
