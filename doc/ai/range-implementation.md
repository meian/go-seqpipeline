# Issue #30: `FromRange` の実装方針

`seq.FromRange` は整数の範囲を遅延生成する入力関数として実装する。  
公開契約と、その契約を満たすための実装上の判断を以下に定める。  

## 公開契約

- `start` と `stop` は同じ整数型 `T` とし、組み込みの符号付き・符号なし整数型と、それらを基底型とする定義型を受け付ける
- `uintptr` を対象に含め、`byte` と `rune` はそれぞれ `uint8` と `int32` の別名として利用できる
- 浮動小数点型は対象に含めない
- 引数順は `FromRange(start, stop, step)` とし、返り値は `Seq[T]`、`step` は環境によらず符号付きの `int64` とする
- `int64` で表せない増減値は指定できない
- `step` が正なら昇順、負なら降順とし、方向が合う場合は `start` と到達した `stop` を含める
- `stop` を飛び越す前に終了する
- `start == stop` かつ `step != 0` なら `start` を 1 件返す
- `step == 0` は関数呼び出し時に panic する
- `step` の符号が `start` から `stop` への方向と逆なら、空の非 nil `Seq` を返す
- 要素の生成は反復時に行い、各反復は `start` から独立して始める
- `yield` が `false` を返したら直ちに停止する
- 整数型の上限・下限を超えて折り返さずに終了し、`step == math.MinInt64` も同じ契約で扱う

## 実装構成

- `seq` に generic な公開関数を置き、シーケンス構築時に `reflect.TypeFor[T]().Kind()` を 1 回調べる
- signed の 5 種と、`uintptr` を含む unsigned の 6 種の `reflect.Kind` を、それぞれ 1 つの反復関数へ振り分ける
- 要素ごとの反射は行わない
- `Kind()` の判定では型パラメータ `T` の制約は狭まらないため、両反復関数は整数型全体の制約を使う
- signed の作業値は `int64`、unsigned の作業値は `uint64` に無損失で変換し、出力時に `T` へ戻して定義型を保つ
- unsigned の値を `int64` 経由で扱わない
- 現在値を反復ごとのローカル状態に置き、途中停止後の再評価に影響を残さない
- `yield` が `false` を返した後は次の値を計算しない
- 次の値を計算する前に終点までの残距離を比較し、飛越しと型の範囲外への折り返しを防ぐ
- 負の `step` の大きさを求める際は `-step` に依存しない
- signed の残距離も符号付き整数の減算だけで求めない
- 空結果でも呼び出し可能な非 nil の `Seq` を返す

## 方式を選んだ根拠

11 型別関数と signed / unsigned の 2 関数を、組み込み型の `type switch` と定義型への `reflect` fallback、および `reflect` のみの分岐で比較した。  
型別関数と 2 関数はいずれも generic であり、非 generic の具象関数は比較していない。  
Apple M4・Go 1.27.3・darwin/arm64・`GOMAXPROCS=1` で、シーケンスの生成と全要素の消費を合わせ、昇順・降順とも `step` の大きさを 1 として測定した。  
比較用実装の `step` は `int` で、測定環境では 64 bit だったため、この結果を `int64` 固定の最終実装の絶対性能として扱わない。  

次は `reflect` のみで振り分けた 2 関数が、型別関数より短い時間で完了した代表条件である。  

| 条件 | 型 | 時間短縮 |
| --- | --- | --- |
| 96 要素の昇順 | `int8` | 29.5% |
| 96 要素の昇順 | `uint16` | 21.2% |
| 96 要素の昇順 | `uint32` | 27.7% |
| 4096 要素の昇順 | `uint16` | 26.5% |
| 4096 要素の昇順 | `uint32` | 36.2% |
| 4096 要素の降順 | `uint` | 6.1% |
| 4096 要素の降順 | `uintptr` | 12.1% |

`type switch` と `reflect` の時間差は、全 81 条件の中央値で絶対値 0.5% 未満だった。  
割り当ては全方式でシーケンスの生成と消費 1 回につき 3 回だった。  
2 関数は一部の型と長い反復で有利で、11 型別関数より実装箇所が少ない。  
`reflect` のみの振り分けにも明確な劣位がないため、2 関数と `reflect` の組み合わせを採用する。  

`int32` の優劣は定まらず、呼び出し回数が多い条件では方式間の差が小さい。  
測定は生成単体と生成済み `Seq` の再利用を分けておらず、1 以外の大きさの `step` も含まない。  
性能を確認するときは最終実装で短い列と長い列、生成ごとの評価と生成済み `Seq` の再利用を分けて測る。  
`ns/op`・`allocs/op` を記録し、測定順を逆にしても差が再現するか確認する。  

## 検証と文書

`seq` の単体テストで端点への到達・飛越し、終点から遠ざかる `step`、0、狭い整数型を超える `step`、最大・最小値、定義型、再評価を確認する。  
`Pipe`・収集・途中停止の連携は単体テストと分けて検証する。  
個別の公開仕様は GoDoc、実行可能な使い方は `seq` の Example に置く。
