## 比較条件

### Pipeline

入力は `0..N-1` の `[]int`、N は 64 / 4096。  
`Seq` は値のみ、`Seq2` はスライスの添字と値を扱い、添字を維持する。  
D2 は Map 1 回と Filter、D6 は Map 5 回と Filter で、Map は `(v + 1) & 65535`、Filter は `v % 3 != 0`。  
All は全件評価、Early8 は Filter 後の 8 件で停止し、パイプラインでは追加の Take 1 段を使う。  
したがって D は Take を除くオペレーター数を表す。  

| 実装 | 処理 |
| --- | --- |
| Loop | 通常のループ内で変換・判定を直接記述 |
| Functions | 要素ごとの変換・判定を `mapValue` / `keepValue` に分離 |
| Pipeline | Seq / Seq2 を構築し、Map / Filter / Take を接続して評価 |

全実装で同じ `[]pair{key, value}` に、nil スライスから append で出力を収集する。  
Seq の key は 0 とし、比較対象も同じ形式にそろえる。  
入力生成は計測外、構築・評価・出力割り当ては計測内で、結果はグローバル変数に保持する。  
構築だけの測定は行わない。  
Functions は処理段階ごとにスライスを実体化する方式ではなく、要素ごとの関数呼び出しであり、インライン化される可能性がある。  

### Channel

N は 64 / 4096、処理は D2 の Map / Filter と同じで、全件を同じ append 条件で収集する。  
途中終了やキャンセルはこの測定の対象外。  
コンテキストは `context.Background()`、ToChannel の出力容量は API の契約どおり常に 0。  

| ケース | 構成 | 対照 |
| --- | --- | --- |
| Seq | 呼び出し元で Seq を直接反復 | — |
| ToChannel | Seq → ToChannel → 受信。送信用 1 goroutine | Seq |
| Direct | 入力送信用 1 goroutine → channel → 呼び出し元で変換・判定 | — |
| FromChannel | 同じ送信者 → channel → FromChannel → Map / Filter | 同じ容量の Direct |
| RoundTrip | 同じ送信者 → channel → FromChannel → Map / Filter → ToChannel → 受信。計 2 goroutine | 同じ入力容量の Direct |

Direct / FromChannel / RoundTrip は入力 channel の容量 B を 0 / 64 に変える。  
入力スライス生成を除き、channel 生成、goroutine 起動、全送受信、close の観測、送信者の終了待ち、変換・評価・出力収集を計測に含める。  
追加の変換に必要な channel・goroutine 自体も比較するコストに含める。  
出力を読み切り、入力送信者の終了通知を待つため、次の反復に送信待ちの処理を持ち越さない。  

### Cache

N は 64 / 4096、Seq / Seq2 の Map で各値に `v = (v * 1664525 + 1013904223) & 65535` を W 回適用する。  
W0 は軽い上流、W32 は算術負荷のある上流を表し、Seq2 のキーは元の添字を維持する。  
出力は全件を int64 のチェックサムに加算し、グローバル変数に保存する。  
比較対象には同じ評価・加算条件を使い、下流の出力スライスは作らない。  

| ケース | 測定範囲 |
| --- | --- |
| Fill | 上流構築 + Cache / Cache2 の作成・全件保存。保存結果を保持し、下流の反復は行わない |
| Warm | 計測前に全件保存済み。計測内では保存結果を 1 回反復して加算 |
| R1 / R4 / R16 の Raw | 上流構築 + キャッシュなしで R 回評価・加算 |
| R1 / R4 / R16 の Cached | 上流構築 + 初回全件保存 + 保存結果を R 回反復・加算 |

Cache / Cache2 は呼び出し時に全件評価するため、Fill が初回保存に相当する。  
R は下流が結果を利用する回数で、Cached の保存時には上流をさらに 1 回評価する。  
Cached / Fill は測定反復ごとに新しいキャッシュを作り、Warm だけが事前作成したキャッシュを使う。  
Warm と R1/Raw の比較は、構築・保存を除いた再利用コストの参考比較であり、初回費用を含む公平な合計比較には同じ R の Cached / Raw を使う。  

| N | 保持する要素数・組数 | Seq の値データ | Seq2 のキー・値データ |
| ---: | ---: | ---: | ---: |
| 64 | 64 | 512 bytes | 1024 bytes |
| 4096 | 4096 | 32768 bytes | 65536 bytes |

arm64 の int は 8 bytes として計算した論理データ量で、スライスの余剰容量やヘッダー、クロージャーは含まない。  
B/op は途中の拡張時に破棄する領域も含む割り当て総量であり、保持データ量とは異なる。  
初回保存には要素数に比例する保持メモリが必要で、Warm の B/op に保持済みの領域は含まれない。  

## 出力の等価性

`TestPipelineEquivalent` は空入力・1 件・64 件・4096 件について、全条件の出力値・キー・順序をスライス比較する。  
`TestChannelEquivalent` は同じ入力群で、全構成・容量の出力値・順序を確認する。  
`TestCacheEquivalent` は同じ入力群・上流負荷でキャッシュ前後の値・キー・順序を比較し、16 回の再利用でも期待チェックサムが一致することを確認する。  
これらは時間計測と分離した通常のテストとして実行する。

### 入力件数・段数・途中終了

Seq の N4096 / All では、D2 の Pipeline は Loop の約 1.98 倍、D6 は約 3.12 倍だった。  
Seq2 の D6 も約 3.38 倍で、この軽い算術処理では段を接続するコストが目立つ。  
D2 / Seq / All の Functions は 12839 ns/op、Loop は 12425 ns/op で、差は約 3.3% にとどまった。  
要素ごとの関数に分けてもインライン化を許す比較なので、関数境界の維持を強制した呼び出しコストを表す値ではない。  

Early8 の Pipeline は、Seq / D6 で N64 が 356.0 ns/op、N4096 が 366.1 ns/op だった。  
必要な出力がそろうと上流も止まるため、このケースでは入力の全件数よりも、接続・停止処理と先頭の必要件数の処理が支配的と考えられる。  
All では入力を増やすと評価と出力収集が増える一方、Early8 では固定の構築費用の割合が大きい。  
これらの時間には出力の append と割り当ても含むため、値の反復だけのコストとは区別する。  

### Channel の変換と容量

N4096 / B0 では FromChannel は Direct の約 1.17 倍、往復変換は約 1.99 倍だった。  
B64 では Direct と FromChannel の両方が B0 より短時間になったが、FromChannel の Direct に対する倍率は約 1.66 倍になった。  
入力容量の変更で対照自体も変わるため、絶対時間と倍率の両方を確認する必要がある。  
ToChannel は Seq 直接反復の約 23.45 倍で、この小さな処理では送受信・goroutine 起動を加える費用が大きい。  
RoundTrip の追加 goroutine とバッファなし出力も含む結果であり、遅い外部 I/O と組み合わせる場合の優劣はこの測定から判断できない。  
容量の効果は入力側だけの比較で、ToChannel の出力容量を調整した測定ではない。  

### キャッシュの初回費用・再利用・メモリ

N4096 / Seq / W0 の Cached は R1 では Raw より遅く、R4 では短時間になった。  
W32 でも R1 は初回保存の費用で遅く、R4 では Raw の約 0.33 倍、R16 では約 0.13 倍になった。  
Seq2 / W32 / R16 も約 0.14 倍で、上流の処理が重く、同じ結果を何度も利用するほど再評価の省略が効く条件だった。  
今回測った利用回数は 1 / 4 / 16 のみで、厳密な損益分岐回数は求めていない。  

W32 / N4096 の Fill は Seq が 78361 ns/op、Seq2 が 84656 ns/op。  
Warm はそれぞれ 4760 ns/op、5409 ns/op だが、保存に要する時間と保持メモリを計測外にした値である。  
Warm にも反復用の割り当てが 40 B/op・2 allocs/op あり、割り当てが完全になくなる結果ではなかった。  
R16 / W32 での割り当て総量は、Seq が 129088 B/op、Seq2 が 260152 B/op で、Raw の 752 B/op より多い。  
キーも保存する Seq2 は値だけの Seq より保存量が増えるため、時間短縮と保持メモリの交換として判断する。  

## ばらつきと結論の範囲

各ケースの 5 回測定の CV は、Pipeline が中央値約 0.81%・最大約 13.32%、Channel が約 0.53%・最大約 3.80%、Cache が約 0.44%・最大約 2.52% だった。  
最小–最大は観測範囲であり、信頼区間ではない。  
1 回 100ms の短い測定をケース順に 5 回ずつ行っており、順序のランダム化、CPU の固定、温度・周波数の制御やバックグラウンド負荷の測定は行っていない。  
熱状態・OS スケジューリング・GC・他の処理の影響は排除できず、僅かな差だけで性能差を断定しない。  

今回の範囲では、軽い処理での段数増加、channel の追加、キャッシュの初回保存に追加コストを観測した。  
途中終了は不要な上流評価を抑え、複数回使う重い上流ではキャッシュによる合計時間の短縮を観測した。  
CPU・Go バージョン・データ型・出力方式・上流負荷が変われば数値や有利な条件も変わるため、一般的な速度保証としては扱わない。  
性能改善を検討する際は、該当ケースをより長い benchtime で再測定し、必要に応じて専用 Issue に実アプリの処理負荷を追加する。
